## TOP UNRESOLVED ISSUE — heading drift hypothesis

User observation: on a flat-stationary phone after fresh cal, the heading in the
viewer UI counts up at ~1°/s consistently. After ~15 min of stationary time it
settles to ~0.16°/s per logcat measurement (`v39_drift.logcat.txt`).

**User's hypothesis (worth investigating)**: maybe the camera is causing the
rotation. Visual VO running on a stationary scene with KLT subpixel noise could
produce non-zero apparent-rotation residuals, which the EKF accepts as
measurements of true rotation, contaminating the bias estimate.

**Tests for tomorrow's agent**:

1. **Camera-off experiment**: temporarily comment out the camera pipeline (or
   set `cameraVisible=false`, or use airplane-mode equivalent for the visual
   stack) and check whether stationary heading drift drops cleanly to the
   gyro-bias-RW floor (Allan predicts <0.05°/s).
2. **Inspect `updateGravityAlignedYaw` firing rate during static**: grep
   logcat for the function call site (or add LOGI if not present). If it
   fires during truly stationary periods, check what `target_yaw` it computes
   from visual input — that's a non-zero rotation injection.
3. **Inspect visual rotation residuals**: log `r_R` from `updateRelativeRotation`
   during static. If `|r_R|` is non-zero on stationary scene, KLT-derived
   rotation is non-trivially polluting the filter.
4. **MSCKF projection contribution**: even if the static-gate filters most
   MSCKF updates, check `msckf_update_lines` count during static — should be
   zero. If non-zero, there's a leak in the static gate.

If hypothesis confirmed (visual injecting rotation during static), the fix is
ONE of:
- Tighten the visual rotation gate during `is_static`
- Block `updateGravityAlignedYaw` entirely when `is_static`
- Increase the `sigma_axis_sq` for visual rotation measurements to neuter them

If hypothesis NOT confirmed (drift is pure gyro), then σ_bg=1e-5 is too tight
to absorb the cal-init bias error within practical time. Tomorrow's agent
should ship σ_bg schedule (start at 1e-3, decay to Allan 7.46e-7 over 5 min)
— it's the cleanest fix.

### 1. CRITICAL — `EKFState.cpp:502-508` velocity clamp at 5 m/s
**75% of frames in v29 hit the clamp.** This is a defensive clamp swallowing

### 2. CRITICAL — `Tracker.cpp:3935-3984` `applyLandmarkObservations` disabled
Phase 6.4 LandmarkMap-to-EKF update path is commented out after a v28
4× position runaway. The whole LandmarkMap pipeline runs (add/merge/cull/match)
but nothing reaches the EKF. **The runaway has no identified root cause** — so
the fix can't be validated until tomorrow's agent root-causes it. Without this,
loop closure cannot close global consistency through the landmark map. Highest
strategic value for 1km goal.

### 3. HIGH — `Tracker.cpp:1213` P_pp covariance collapse
Tier 1 `setPosition(global_t_)` revert continuously zeroes the EKF's position
uncertainty. Every Kalman gain (MSCKF, PDR, LC) is computed as if position is
known to machine precision → gain blows up → corrections overshoot. Probably
load-bearing for the LC chi² rotation residual showing `|r_R|=135°` in v33.
Fix: don't reset P_pp on setPosition, propagate it forward correctly. Risk: if
not done carefully, dead-reckoning bug from Tier 1 returns.
